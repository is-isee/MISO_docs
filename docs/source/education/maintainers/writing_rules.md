# MISO education の執筆ルール

MISO education は、Fortran で数値計算コードを書いてきた人が、MISO の C++ コードを
**読めて、直せて、足せる**ようになるための教材です（MISO_docs #25）。
構成と書き方は堀田の R2D2_education に合わせています。
このディレクトリ（`education/maintainers/`）は Sphinx のビルドから除外しており、Pages には出ません。

## 置き場所

| 場所 | 役割 |
|---|---|
| `education/index.md` | 読者向けの入口と本文の順序（目次） |
| `education/01_*.md`〜`11_*.md` | 本文 11 章 |
| `education/reference/` | 用語集、Fortran との対応表、記号の早見表などの参考資料 |
| `education/practice/` | 本文から案内する実習の仕様 |
| `education/maintainers/` | 執筆ルール、執筆計画、作業ログ、実習の解答例（公開しない） |

## 対象読者と前提

- 前提にするのは、Fortran の変数・配列・ループ・サブルーチンを読めることです。
  Fortran の派生型・ポインタ・モジュールの高度な機能、C++ の知識は前提にしません。
- MISO は公開リポジトリです。読者は MISO を clone したフォルダから、本文に示すパス（`miso/include/miso/execution.hpp` など）を辿ります。
- 教材自身の保存場所や執筆者個人の絶対パスは書きません。コマンド例では `/path/to/MISO` のように、読者が置き換えるパスを明示します。

## 教材を書くときの作法

**1. コードは受講者が書きます。**
実習の `CMakeLists.txt` や `main.cpp` は、教材側が完成品として渡しません。
「何を作るか」「なぜそう書くか」を説明し、受講者が自分で書いてビルドします。
環境構築では、道具が動くかを確かめる短い確認プログラムとビルド設定を載せてよいです。
宣言や値の変化を確かめる短い文法例も載せてよいです。説明用の例と、MISO の抜粋は区別します。
実習の解答例は `maintainers/solutions/` に置き、本文からは案内しません。解答例は実際にビルド・実行して確かめます。

**2. 章内の練習には解答・解説を付け、折りたたみます。**
問題文は折りたたみの外に置き、解答は次の形で閉じた状態にします（`open` 属性は付けません）。
Markdown を正しく表示するため、`<summary>` の次と `</details>` の前に空行を入れます。

```html
<details>
<summary>解答・解説</summary>

（ここに Markdown）

</details>
```

**3. 読者が必要な順に学べる構成にします。**
本文は 4 部・11 章です（`maintainers/plan.md`）。各章・各練習は、それまでの章の知識だけで読めるようにします。
後の章で学ぶことに触れるときは「第 N 章で説明します」と書いて先へ進みます。
CPU だけで進める道筋（第 1〜8 章 → 第 10 章の逐次・MPI 部分 → 第 11 章）を保ちます。GPU の章は GPU がなくても読めるようにします。

**4. C++ の第 2〜6 章は、すべての節で文法や考え方を主題にします。**
各節で、小さな説明用の例に続けて、対応する MISO の実例を置きます。MISO の実例を章末にまとめて置くことはしません。
長い実例は分けて、必要な文法を学んだ直後に読めるようにします。

**5. MISO のコードを引用したら、パスを書きます。**
`miso/include/miso/array3d.hpp` のように、MISO リポジトリの根からのパスを書きます。行番号は変わりやすいので書きません（関数名・クラス名で示します）。
抜粋は必要な部分だけにし、説明のためにコメントを足したときはそのことを明記します。
引用は MISO の `main` ブランチの内容に合わせます。

**6. 文体**
- 本文は「です・ます」調です。導入や説明では読者への問いかけを使わず、内容を直接説明します。
- 課題は疑問文にせず、「〜を説明してください」「〜を確かめてください」のような依頼形にします。
- 見出しは扱う内容が分かる名詞句にします（「参照の使い方」「クラス・構造体」）。「まず地図」「いちばんの山」のような書き手のメモにしません。
- AI や執筆者の苦労、開発中の失敗談を本文に持ち込みません。開発履歴は `maintainers/` に置きます。
- 故意にコードを壊すことを実習の必須条件にしません。

**7. Fortran の経験を足がかりに、C++ を基礎から説明します。**
「Fortran の派生型と同じ」と言うだけで済ませず、型・名前・初期値・関数の宣言から順に説明します。
`if`・`for` なども既知とせず、ループの上限（C++ は 0 始まり・上限を含まない）など、似ていても意味が違う点を補います。
同じ記号でも宣言と式で意味が変わること（`*`, `&`）、`const` の位置で制限の対象が変わることを、短い例で示します。
動きを追いにくいコード例には、どの変数が変わるか、何を参照するかを行の近くにコメントで書きます。

**8. 新しい用語は、役割を説明してから使います。**
「何をしたいか」→「値や処理がどう変わるか」→「その仕組みの名前」→「MISO の実物」の順を基本にします。
慣れない語を使ったら、`reference/glossary.md` に英語を併記して足します。用語集に足すだけでは本文での説明の代わりになりません。

**9. 興味を広げる話題は、折りたたみの「コラム」にします。**
`<summary>コラム：話題の名前</summary>` を付けて閉じた状態にします。コラムを読まなくても次の本文へ進めるようにします。
歴史や設計意図は一次資料（規格、設計者の論文・マニュアル）で確かめ、リンクを添えます。確かめられた事実と推測を分けます。

**10. MISO の語彙**
- バックエンドは `backend::Host`（CPU）と `backend::CUDA`（GPU）の 2 つです。タグ型（中身のない型）で選びます。
- 並列ループは `miso::for_each`、縮約は `miso::reduce`（`miso/include/miso/execution.hpp`）。ラムダは `MISO_LAMBDA`（同じ `execution.hpp` で定義。`cuda_compat.hpp` は CPU ビルドで `__host__`・`__device__` を空にするだけ）で書きます。
- 配列は所有する `Array1D`〜`Array4D` と、所有しない軽い `View`（`Array3DView` など）を区別します。
- 他のプロジェクトの非公開コードは引用しません。

## Sphinx（MyST）の書き方

- 本文は MyST Markdown です。数式は `$...$`、`$$...$$` が使えます。
- 章・節のラベルは `(edu-ch07-for-each)=` のように見出しの直前に置き、参照は `` {ref}`表示文 <edu-ch07-for-each>` `` で書きます。ラベルはすべて `edu-` で始めます。
  章のラベルは `edu-ch01`〜`edu-ch11`、参考資料は `edu-ref-<名前>`、実習は `edu-practice-<名前>` です。
- コードブロックの言語名は `cpp`, `cuda`, `fortran`, `bash`, `cmake`, `yaml`, `text` を使います。
- 他章のファイルへのリンクに `.md` の相対パスを使わず、ラベルを使います。
- 長い章には冒頭に目次を置きます（`` ```{contents} `` ではなく、節へのラベル参照の箇条書き）。

## 検査

- `sphinx-build -W` で警告なしにビルドできること（未定義ラベル、toctree に入っていない文書を検出します）。
- 実習の解答例と、本文の「動かして確かめる」例は、実際にビルド・実行して確かめます。
- 本文の前提関係（未習の記号・語を使っていないか）、本文と解答の整合性を読み直します。
